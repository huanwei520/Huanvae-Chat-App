# 代码质量审核（独立 Agent）

在代码实现和测试编写阶段，启动独立审核 Agent 进行严肃的代码质量检查。**调用两次**：代码写完一次，测试写完再一次。

## 触发时机

| 阶段 | 触发条件 | 审核重点 |
|------|----------|----------|
| 代码实现后 | 业务代码编写完成，测试尚未开始 | 无用兜底、过度防御、死代码 |
| 测试编写后 | 测试代码编写完成，自检尚未开始 | 假测试、无效断言、覆盖缺失 |

### A 组 · 检查器自身失效（它不会红）

#### A1 · `OUT=$(cmd) || true` 之后再取 `$?` ⇒ 恒 0、结构上不可能 FAIL

`||` 属于**整条命令列表**，`OUT=$(cmd) || true` 整体总是成功 ⇒ 紧随的 `$?` 取到的是那个整体的
退出码（恒 0）⇒ `if [[ $EXIT -ne 0 ]]; then FAIL; fi` 结构上进不去。

**判据（两步：先筛、再逐条打开 —— 第二步不能省）**

```bash
# ① 列出所有 `|| true`
grep -n '|| true' scripts/linux/test-all.sh scripts/test-all.ps1

# ② 粗筛「附近就读 $?」的可疑处（有假阳性，见下）
grep -nA3 '|| true' scripts/linux/test-all.sh | grep -E '=\$\?'
```

🔴 **② 是筛子，不是判决。** 实测本仓 ② 输出 **2 行，逐条打开后两行都不是缺陷**：
`:301` 是**解释本规则的注释行**（注释里本来就写着 `|| VAR=$?`），
`:304` 是 `ESLINT_OUTPUT=$(pnpm lint 2>&1) || ESLINT_EXIT=$?` —— **正确写法**，只是恰好落在
`:301` 之后 3 行内被 `-A3` 捎带出来。⇒ **命中必须逐条打开看原文**；只看「② 非空」就下结论会误判。
（这是 C10 的镜像形态：C10 防假阴「0 命中未必真没有」，这里防假阳「有命中未必是那类行」。）

**判 FAIL**：逐条打开后确有某处 —— **同一条命令**写成 `OUT=$(cmd) || true`，而**紧随的下一条
语句**是 `XXX=$?` ⇒ 该步骤恒 PASS；若其 `then` 分支内**没有别的 FAIL 出口**，
该步骤**历史上的绿一律不构成「真跑通过」的证据**。

**别误伤**：`X=$(cmd || true)`（`|| true` 在命令替换**内部**）且**不与 `$?` 配对**是正当写法。
判据是「**有没有紧跟着读 `$?`**」，不是「有没有出现 `|| true`」。

**现查（2026-08-12，本机实跑）**：`scripts/linux/test-all.sh` 现存 **2** 处 `|| true` ——
`:301` 是解释本规则的**注释**、`:380` 在命令替换内且不与 `$?` 配对（**均为正当**）；
`scripts/test-all.ps1` 现存 **0** 处。历史上的「6 处、活了近三个月」已由 commit `2f3e4dd` 修掉。

**同族两形态（🔴 由 review 实证补入，原清单遗漏）** —— 判据都是同一句话：
**这条分支进得去吗？它的结论进最终汇总了吗？** 两条均为 2026-08-12 本仓实测，
来源 `.claude/rules/common.md`「同族的第三态」一节：

- **A1-a · `⚠ WARN` 既不 FAIL 也不登记进跳过表 = 门禁的第三态「隐形跳过」**
  判据：`grep -n 'WARN' scripts/linux/test-all.sh scripts/test-all.ps1`，命中处逐条打开，
  问「它的结论有没有进末尾汇总」。**判 FAIL**：只打一行黄字就过去、末尾汇总里看不见 ——
  它既不是 PASS 也不是 FAIL、也不在跳过表里，等于门禁里一个**没人看得见的第三态**。
  实证位置：`test-all.sh:155` / `:162`、`test-all.ps1:131` / `:137`。
- **A1-b · 恒假的死分支（看着在把关，其实没把）**
  形如 `cmd | grep -q X | grep -v Y` 的管道：`grep -q` **不产出任何输出**，
  下游同管道的 `grep -v` 拿到空输入必返回 1 ⇒ **整条 `if` 恒假**，永远进不去。
  **判据不是读代码，是实跑**：构造一份**确实含 X** 的输入喂进那条管道，看条件真假；
  **正对照**单跑 `grep -q` 必须能命中（rc=0），否则证明不了「假」是管道造成的。
  实证位置：`scripts/linux/test-all.sh:378`（前端构建查 Vite 警告那条，**至今未修**）。

#### A2 · CI 触发条件写错 = 这个 workflow 从没跑过

**判据（离线，可机械跑；本条优先）**：把 workflow 的 `paths:` / `working-directory:` 前缀
拿去 `git ls-files` 对一次，**0 命中 = 该 workflow 结构上永不触发**。

```bash
grep -nE "paths:|working-directory:|'[A-Za-z0-9_.-]+/\*\*'" .github/workflows/*.yml
git ls-files | grep -c '^<上面取到的前缀>/'      # 必须 > 0
git ls-files | grep -c '^\.github/'              # 正对照：已知存在的前缀，必须 > 0
```

**判据（在线）**：`gh run list --workflow=<文件名> --limit 5` **非空**才算它真跑过。
「文件存在」「YAML 语法对」**都不算**。（本机 `gh auth status` rc=1 未登录 ⇒ 以离线判据为准。）

**判 FAIL**：前缀在 `git ls-files` 里 0 命中，而正对照 > 0 ⇒ 触发条件写错，该 workflow 是死的。

**现查（2026-08-12，本机实跑，这是仍然存在的真缺陷）**：
`.github/workflows/test.yml:6-9` 写 `paths: - 'Huanvae-Chat-App/**'`，`:12-14` 写
`defaults.run.working-directory: Huanvae-Chat-App`；而 `git rev-parse --show-toplevel` =
`…/work/Huanvae-Chat-App` **本身就是仓根**，其下**没有**同名子目录
（`git ls-files | grep -c '^Huanvae-Chat-App/'` = **0**，正对照 `^\.github/` = **3**）
⇒ 该 workflow 结构上永不触发。**本清单只把它当范例，修它属另单。**

#### A3 · 空集静默跳过：空目录 = 什么都没做，却不报错

```bash
for f in dir/*; do [ -f "$f" ] || continue; ... done
```

`dir/` 为空时 glob 不展开、`[ -f ]` 失败、`continue` 跳过 ⇒ **一次循环体都没进，退出码仍是 0**。

**判据**

```bash
grep -nE 'for [A-Za-z_]+ in [^;]*\*' .github/workflows/*.yml scripts/linux/*.sh
grep -nE '\|\| continue|\|\| break' .github/workflows/*.yml scripts/linux/*.sh
```

**判 FAIL**：命中的循环**没有**配套的「至少处理了 N 个」计数断言
（如 `n=0; …; n=$((n+1)); done; [ "$n" -ge <期望> ] || exit 1`）。

**范例（现查确认原文）**：`.github/workflows/release.yml:810-811`
`for file in r2-upload/*; do` / `[ -f "$file" ] || continue` —— 上游 `gh release download` 若
一个产物都没下到，这里**静默零次上传**，然后照常走到 `:830` 打印成功。

🔴 **上面那两条 `grep` 是筛子，不是判决 —— 命中必须逐条打开读原文。**

**别误伤**：循环的空集情形**若由下游的显式退出兜住**（形如紧随其后的
`if [ -z "$VAR" ] || [ ! -d "$VAR" ]; then echo …; exit N; fi`），即为**正当写法**，
**不判 FAIL** —— 它只是没有用「计数断言」的形式，语义上已经把空集堵死了。
判 FAIL 的真正条件是「**空集会一路走到成功路径**」，不是「没写计数断言」。

**假阳性范例（现查确认原文，本仓正当写法，2026-08-12 review 实撞）**：
`scripts/linux/test-all.sh:513-520` 的 NDK 候选路径探测循环
（`for c in "$NDK_HOME" … /opt/android-ndk; do [ -n "$c" ] || continue; …; done`）
被本条判据命中，但它**不是缺陷**：紧随其后的 `:521-524`
`if [ -z "$NDK" ] || [ ! -d "$NDK" ]; then echo …; exit 20; fi` 把空集堵死了。
按本条**字面**的判 FAIL 条件（「没有计数断言」）它会被误判成缺陷 ⇒ 这一段就是为了防这个。
（与 A1 的「② 是筛子不是判决」写法对齐；同属 C10 的镜像形态 —— C10 防假阴，这里防假阳。）

#### A4 · 无条件的成功宣告：前面没有任何断言

**判据**

```bash
grep -nE 'echo .*(✅|SUCCESS|全部通过|All .* (uploaded|passed|succeeded))' \
  .github/workflows/*.yml scripts/linux/*.sh scripts/*.ps1
```

**判 FAIL**：逐条向上读到该 step / 函数开头，这中间**没有任何** `exit` / `|| exit` /

#### A5 · 缺「产出齐不齐」的断言：只数个数 / 用通配符，没有显式必需清单

grep -nE 'gh release download|aws s3 cp|-p "\*' .github/workflows/release.yml
grep -cE 'REQUIRED_(ASSETS|FILES)|EXPECTED_(ASSETS|FILES|COUNT)|必需清单|必需产物' \

#### A6 · 测量方法本身错：观测动作改变/错开了被测对象的时间线

**判据（提问 + 可指认的 file:line）**：任何**观测型**检查（E2E 探针 / CDP 监听 / 采样 / 计时窗），

### C 组 · 判据本身会坏（你测的不是你以为的东西）

#### C10 · 零命中可能是查法错

🔴 **任何「没有 / 为 0 / 查不到 / 不存在」的结论，必须先跑正对照** ——
拿一个**已知存在**的目标喂给同一条命令，确认它真能命中。

```bash
grep -c '<你要证明不存在的东西>' <范围>    # 你的结论：0
grep -c '<同范围内已知存在的东西>' <范围>  # 正对照：必须 > 0，否则 0 是盲区不是结论
```

**判 FAIL**：报告里出现「0 处 / 无 / 不存在」而**没有**配套正对照命令与其非零输出。

**同族陷阱（仓内已有多例，见 `.claude/rules/common.md`）**：字符类漏数字
（`[A-Z_]` 不匹配 `GITHUB_PAT_RELEASE2024` 里的 `2024`）、时间窗选错
（启动类日志只在启动那一瞬打印一次，`--since -6h` 对已连跑数天的服务必然 0 命中）。

#### C11 · 判据选错地址 / 对象

**判据**：探测目标（地址 / 端口 / 进程名 / 二进制）必须**来自配置真值源的 `file:line`**，
不能手写；命令本身也要防自匹配与环境影子。

```bash
ps -ef | grep '[g]it'          # 字符类写法，避免 grep 匹到自己
command -v grep && grep --version | head -1   # 确认没被 ugrep / busybox 影子
```

**判 FAIL**：结论建立在「我探了 X 得到拒绝」上，而 X 并非真值源里那个地址 / 对象。

**实证**：探 `127.0.0.1:2222` 得拒绝，而真地址在 `192.168.64.1`；`ps` 匹到自己；
`grep` 被环境影子成 `ugrep` 导致两侧行为不一致。

#### C12 · 测错了界面 / 对象

**判据**：界面类缺陷，**必须逐字复述报障人给的路径**（几级菜单、点哪个分类、哪个 tab），
并在证据（截图 / 录屏 / DOM 摘录）里**看得见该路径的标题文字**。

**判 FAIL**：证据取自另一个界面 / 另一个入口 ⇒ 该证据不算，「不复现」结论作废。

**实证**：视频封面缺陷报障在**「查找聊天记录 → 视频」分类**，而验证测的是**聊天气泡**
（那里本来就是好的）⇒ 得出「不复现」，白跑一轮。
配套两条同族假阴（见 `.claude/rules/common.md`「不复现有三种假法」）：
**样本量不足**（12 条零重叠、60 条才炸出 210 对重叠）、**判据形态错**（命中 4 处全是注释）。

### D 组 · 完成度判据

#### D13 · 「发布完成」是时间窗，不是瞬间

git 侧秒级成立，分发侧要等最慢的那个 CI job（本仓实测约 **18~23 分钟**）
⇒ 判 PASS 的那一刻，产物可能还是 404。

**判据：必须同时给两面读数 + 各自的采集时刻。**

```bash
date -u +%FT%TZ                                        # 采集时刻，两面各记一次
git ls-remote --tags origin | grep '<版本 tag>'        # git 面
curl -s  '<latest.json URL>' | grep -o '"version":[^,]*'   # 分发面①：版本号翻没翻
curl -sI '<产物 URL>' | head -1                        # 分发面②：产物 HEAD 状态码
```

**判 FAIL**：只给 git 面读数（tag 推上去了 / commit 在了）就判「已发布」。

#### D14 · 尺寸相同 ≠ 同一份文件

**判据：判「是不是同一份」只用内容哈希或 ETag，不用 size。**

```bash
shasum -a 256 <文件A> <文件B>
curl -sI '<URL>' | grep -i '^etag:'
```

**判 FAIL**：用 `ls -l` / `wc -c` 的字节数论证「这两个是同一份 / 没变」。

**实证**：AppImage 两个版本**字节数完全相同**、ETag 不同 ⇒ 内容其实不同。

### 失效形态清单必答块（review 交付必须原样带上；缺块 = 本次 review 未完成）

🔴 **这一节问的不是「你读了吗」，是「你用它查出了什么」。**
问「读了吗」的问卷**结构上就是可敷衍的** —— 复述条目即可，不需要真读、更不需要真用。
实证：把命令格填 `echo hi`、输出填 `hi`、结论只写「不适用」，下面三条机械核对**全部放行**。
⇒ 每一格要填的是**产出**：**你在哪个文件的哪一行查出了什么**，不是「我跑了什么命令」。

**默认必答 3 条：A2 / A5 / B7**；任务卡可在 `required_reads:` 之后追加指定条目（追加即必答）。
**三态都必须落到具体处**：

| 判定 | 这一格必须给什么 |
|---|---|
| **命中** | `file:line` + 一句「它为什么是这一形态」 |
| **未命中** | 实际撞过的判据命令 + 输出摘要；**零命中结论必须配 C10 正对照**（且正对照非零） |
| **不适用** | 具体理由（「本次 diff 只有 `.md`，物理上没有 shell 分支可恒假」这种），**不接受**「无 / 已检查 / 未发现问题」 |

```markdown
### 失效形态清单必答块

<!-- FMC-ANSWER:BEGIN -->
| # | 判定 | `file:line` 或具体理由（产出，不许空泛） | 实跑判据命令 + 输出摘要 |
|---|---|---|---|
| A2 | 命中 | `.github/workflows/test.yml:6-9` 触发前缀在仓内 0 命中 ⇒ 结构上永不触发 | `git ls-files \| grep -c '^<前缀>/'` → `0`；正对照 `^\.github/` → `3` |
| A5 | 命中 | `.github/workflows/release.yml:788-794` 纯通配下载 + 失败被吞，全链无必需产物清单 | `grep -cE 'REQUIRED_(ASSETS\|FILES)…' …` → `0`；正对照 `aws s3 cp` → `3` |
| B7 | 命中 | `src/` 内该关键词 10 处命中**逐条打开全是注释**，零可执行语句 | 裸 `10` / 剥注释后 `0` |

```

#### 清单逐条应用结果（质量门 —— 必答块只管形式，这一节才管有没有真用）

**review 交付必须另有一节「清单逐条应用结果」**：对**本次 diff 涉及的每个文件**，
把 14 条逐条拿去撞，给出 **命中 / 未命中 / 不适用** 三态之一，填写口径同上表
（命中给 `file:line`、不适用给具体理由、未命中给实跑判据与正对照）。
按**文件**组织，不必写成 14 × N 的方阵：每个文件列出「适用哪些条目 → 各自判定 → 命中处 `file:line`」即可。

⚠️ **这一节的表格行首必须是文件名，不许用条目编号开头** —— 否则会被下面核对②的
`^\| [A-D][0-9]+ \|` 一起数进去，把必答条数撑爆（报告里除必答块外的所有表格同理）。

🔴 **反向判据（比正向更硬，先看这条）**：
**若整份 review 的清单应用结果里 14 条全部是「未命中 / 不适用」，且没有任何一条给出 `file:line`
⇒ 视为「未真正应用」，本次 review 未完成。**
（与总纪律「全绿必须能演示会红」是同一条纪律：一份**什么都没撞到**的清单，
先怀疑的是撞法，不是"本仓真干净"。）

**机械核对（leader / 判官侧，三条命令，任一不满足即判「没读清单」、review 打回重做）**：

```bash
grep -c 'FMC-ANSWER:BEGIN' <review 交付文件>              # 必须 == 1
grep -cE '^\| [A-D][0-9]+ \|' <review 交付文件>           # 必须 == 本次指定的必答条数（默认 3）
grep -cE '^\| [A-D][0-9]+ \|[[:space:]]*\|' <review 交付文件>   # 必须 == 0（紧跟条目号的那一格不许留空）
```

🔴 **这三条只是形式门，管不了质量。** 它们能拦下「缺块 / 少答一条 / 有空格」，
**拦不住答得敷衍** —— 质量由上面的「三态填写口径」+「清单逐条应用结果」+「反向判据」管。
下面这段自陈是本仓既有标准（`.claude/rules/frontend-test.md`：静态契约测试要写清自己防不住什么，
别让读者以为它是全覆盖）。

**本机械核对防不住什么（四类，2026-08-12 实测样本 `rv-LAZY` 全部放行）**：

1. **敷衍命令** —— 任何非空字符串都算「填了」，命令与被答形态毫无关系也照过（`echo hi` 即可）。
2. **编造输出** —— 三条 `grep` **不复算命令**，输出栏可以是编的（真正的解法是把必答块里的
   命令纳入可复算池让 collector 复算；A2/A5/B7 全是纯 `grep`，天然可复算）。
3. **只写「不适用」不给理由** —— 文档要求写清「为什么物理上够不着它」，但**没有任何机械判据**在查这一点。
4. **追加条目与期望值靠人手同步** —— 任务卡追加必答条目时若 leader 忘了把 ② 的期望值一起调大，
   **少答不会被发现**。

⚠️ **只有「审这套机制本身」的人才会撞到的一个坑**（2026-08-12 review 实撞并规避）：
核对①要求起始标记**恰好 1 次**，而一份**审这套机制**的报告天然想引用模板原文 ——
一旦把完整标记字面量写进正文，标记就变成 2 次，**报告自己被①拦下**。
⇒ 写这类报告时全程只用文字描述该标记，**绝不写出完整字面量**（与下面「防漂移自检」里
用 `$M` 拼 marker 是同一个理由）。

**本节完整性 + 防漂移自检（改本节后必跑，三条都要）**：

🔴 下面故意用 shell 变量 `$M` **拼出** marker —— **正文、注释、示例里都绝不能出现完整的
marker 字面量**（那一行会被 `sed` 当成范围终点，抽取提前收摊）。本节前两版连踩两次这一脚，
属 C10「判据本身会坏」同族。

```bash
M=FAILURE-MODES-CHECKLIST
A=.claude/skills/code-review/SKILL.md
B=.claude/skills/blind-review/SKILL.md

# ① 14 条一条不少（两份各自数）
grep -c '^#### [A-D][0-9]* · ' "$A"   # 必须 == 14
grep -c '^#### [A-D][0-9]* · ' "$B"   # 必须 == 14

# ② marker 各自只出现一次（> 1 = 正文里混进了字面量，sed 会提前收摊）
grep -c "$M:BEGIN" "$A"; grep -c "$M:END" "$A"   # 两者都必须 == 1
grep -c "$M:BEGIN" "$B"; grep -c "$M:END" "$B"   # 两者都必须 == 1

# ③ 两份 canonical 块逐字节相同
sed -n "/$M:BEGIN/,/$M:END/p" "$A" > /tmp/fmc-a.md
sed -n "/$M:BEGIN/,/$M:END/p" "$B" > /tmp/fmc-b.md
grep -c '^#### [A-D][0-9]* · ' /tmp/fmc-a.md   # 必须 == 14（正对照：抽的是整块、sed 没提前停）
diff /tmp/fmc-a.md /tmp/fmc-b.md               # 必须无输出
```

⚠️ ③ 里那条 `grep -c '^#### …'` **不能省** —— 它是 diff 的正对照：
marker 一旦自撞，两边都只抽出同样的头几行，**diff 照样干净**，
「两份一致」于是变成假阳性。②③ 必须一起看，单看 diff 无输出不构成结论。

## 审查维度

### 0. 🔴 硬性验收：新功能必须桌面端 / 移动端两端对齐（缺一端 = 不通过）

**这是硬指标，不是建议**：任何**新功能**都必须**同时覆盖桌面端与移动端**，
或在交付里**明确写出某一端为何不适用**（并给出理由，不能只说"没做"）。
**只做了一端 = 审核不通过**，严重度按 **Critical** 记。

**为什么加这条**：本仓桌面与移动是**两套独立组件树**，同一功能要各写一份 ——
桌面 `src/components/**`、`src/chat/shared/ChatPanel.tsx` 等；
移动 `src/pages/mobile/**`（如 `MobileChatView.tsx` / `MobileChatList.tsx`）。
"桌面改了移动没跟"因此是本仓**反复发生**的缺陷类型，实例：
- v1.1.22 修掉桌面列表「点头像跳资料页」，**移动端同一交互没跟**，用户再次报障；
- 输入框内容全局共用一份（无按会话草稿），**两端同时存在**却只被当成单端问题。

**怎么查（逐条核对，不许只看 diff 里出现了哪些文件）**：

1. 本次新增/修改的功能，列出它在**桌面**的实现位置（file:line）；
2. 列出它在**移动**的对应实现位置（file:line）；**找不到就是缺一端**；
3. 两端**交互语义是否一致**（同样的点击/键盘/手势产生同样结果），
   不一致要有理由（如移动端无键盘焦点环属合理差异）；
4. 若确实只适用一端（如托盘图标仅桌面、NFC 仅移动），**在报告里点名写清"某端不适用 + 原因"**；
5. 移动端验证必须在**移动形态**下做，**把桌面窗口拉窄不算**。

| 功能 | 桌面实现 | 移动实现 | 交互一致？ | 结论 |
|------|---------|---------|-----------|------|

### 1. 无用兜底代码

检查是否存在以下模式（TypeScript / React）：
- `x ?? fallback` / `x || fallback` 掩盖了本该暴露的错误 — 如果上游（store / API 解包 / props）已保证非空，直接用；如果可能为空且业务需要感知，应显式返回错误 / 显示错误态，而不是静默给默认值
- 空 `catch {}` 或 `catch (e) { console.warn(e) }` 后静默继续，而该错误实际上应中断流程 / 显示错误 UI / 上抛给调用方
- 多余的可选链 `obj?.field`，其中 `obj` 在当前路径已由类型或上游保证存在
- `Array.isArray(x) ? x : []` / `x ?? []` 类兜底，实际数据结构不可能为 undefined / 非数组
- `switch` 的 `default:` 分支处理了联合类型已穷尽的不可能情况（什么都不做）
- 防御性 `structuredClone(x)` / `{ ...x }` 拷贝，在数据流已明确、无共享可变风险时多余
- （`src-tauri/*.rs` 等价物：`unwrap_or_default()` / `unwrap_or(fallback)` 掩盖错误、`match` 无意义兜底分支、错误被 `log::warn` 后静默继续、防御性 `clone()` / `to_owned()`）

**判断标准**：兜底是否有现实的触发路径？如果没有，就是无用兜底。如果有但被静默处理了，就是错误吞没。

### 2. 过度防御

检查是否存在以下模式（TypeScript / React）：
- 对内部函数的返回值做重复校验（上游已保证格式/范围，下游又 validate 一遍）
- 对 TypeScript 类型已保证的字段做运行时 `typeof` / `instanceof` 检查（如参数类型已是 `string`，还 `if (typeof x !== 'string')`）
- 对 Zustand store / Context 已保证初始化的值做多余的 null 检查
- 在 Hook 和消费组件两处对同一个 prop / 参数做相同校验
- `if (!x) return null` / `if (!x) return;` 但 `x` 在当前渲染 / 调用路径中不可能为 falsy
- （`src-tauri/*.rs` 等价物：对 SQLite NOT NULL 字段做多余 `Option` 包装、`if cond { return Err(..) }` 但 cond 不可能为 true）

**判断标准**：该校验是否在保护一个实际可能发生的场景？是否有其他层（类型系统 / store / 上游校验）已经保证了同样的约束？

### 3. 死代码 / 未使用代码

检查是否存在以下模式（TypeScript / React）：
- 新增了组件 / Hook / 工具函数 / 类型但没有被任何地方 import 或使用
- `export` 了但实际只在本模块使用（应改为模块内私有，减少 barrel 噪音）
- import 了但未使用的组件 / 类型 / 工具函数
- 注释掉的代码块（应删除而非注释）
- 预留的 TODO 占位代码没有实际实现
- 违反 CLAUDE.md「个人开发验证期」约束的残留：`@deprecated` 标注但代码仍可被调用、向后兼容 stub、`_` 前缀"保留兼容"参数（应删字段 + 清调用方）
- （`src-tauri/*.rs` 等价物：0 调用方的 `pub fn`、应收窄为 `pub(crate)` 或私有的可见性、未使用的 `use`）

### 4. 🔴 名不副实检查（声称 vs 可执行代码）

**查法与其它维度相反：从「声称」出发去找实现，而不是从 diff 出发去找问题。**

对本次触碰到的每个功能，逐条问：**注释 / 函数名 / 文档声称的这个能力，有没有对应的可执行代码？**

必查的三类声称：

| 声称形态 | 要找到的东西 | 找不到 ⇒ |
|---|---|---|
| 注释/文档说「支持 X」（断点续传、重试、校验、缓存、防抖…） | 真正实现 X 的**可执行语句** | 报「名不副实」，严重度至少 Warning |
| 函数名/变量名承诺行为（`retry` / `resume` / `validate` / `forceScrollToBottom`） | 名字对应的行为真的发生 | 同上 |
| 某个分支/守卫声称能拦住某情况 | 该分支**进得去**，且 `then` 内真有对应出口 | 报「结构上不可达」 |

🔴 **两条硬判据：**

1. **注释不得作为实现证据。** 声称某能力时，引用的 `file:line` **必须指向可执行语句**，
   不能指向注释行、文档块、类型声明。
   > 实证（2026-08-12）：查「有没有强制滚到底」，裸 `grep` 得 **4 处命中** ——
   > 逐条打开发现**全是块注释**（`* - 打开会话：scrollTop=0 即底部`），**零可执行语句**。
   > 只看计数就会得出「有实现」的相反结论。

2. **「有保护 / 有能力」类声称，必须能说明「拿掉它会怎样失败」。**
   演示不了 ⇒ 只能写「**未验证**」，**不许写「已实现」**。
   （这就是变异思维：金丝雀那套「故意弄坏、看检测器报不报红」的原则，同样适用于业务功能。）

**本仓已实证的 5 条「名义存在、实现为空」**（新维度必须能捞出这一类）：

| # | 假实现 | 为什么骗过了此前的 review |
|---|---|---|
| 1 | **断点续传**：名字与注释都在，实际中断后**从头下**，两端皆是 | 历史遗留，不在任何一次 diff 视野里 |
| 2 | 门禁 `OUT=$(cmd) \|\| true` 紧跟 `EXIT=$?` ⇒ **恒 0、结构上不可能 FAIL**，同族 6 处、活了近三个月（**已由 commit `2f3e4dd` 修掉**，此处是回顾不是现状） | 分支存在，但**进不去** |
| 3 | v1.1.28 的 macOS 视频修复**结构上不可能生效**：只改了「已落盘缓存」支路，而视频**从不自动落盘** | 改动本身正确，但**挂在了走不到的支路上** |
| 4 | `onLoadedData` 里 `video.currentTime = 0` —— 本来就是 0、**不触发 seek、不画帧**，却注释成「暂停在第一帧作为缩略图」，**两处都是 no-op** | 纯注释冒充实现 |
| 5 | 「强制滚到底」裸计数 4 处，逐条打开**全是块注释** | 只数命中、没读原文 |

**正对照（说明新维度确实能捞出它们）**：
- 对 #4：按判据 1，声称「暂停在第一帧作为缩略图」就必须指出**哪一行可执行语句**让画面停在第一帧。
  `currentTime = 0` 在 `currentTime` 已是 0 时不触发 `seeking`/`seeked` ⇒ 举不出那一行 ⇒ 当场判「名不副实」。
- 对 #1：按判据 2，声称「支持断点续传」就要说明「拿掉它会怎样失败」。
  一问「App 重启后从哪个字节续」，即暴露分片字节**只活在内存 / 开局 `File::create` 截断** ⇒ 判「未验证」，不许写「已实现」。

### 5. 🔴 本次范围外发现（必须上抛，不许因「不在 diff 里」丢掉）

**这是此前流程缺的那一层。** 上面 5 条能被挖出来，全靠有人在任务卡里**点名要求去查** ——
流程本身不会自动暴露它们，于是「即使 review 察觉了，也没地方报」。

⇒ **发现与本次改动无关、但严重的问题（假实现 / 假门禁 / 长期失效的检查 / 结构上不可达的分支），
必须单列成「本次范围外发现」上抛 leader → 总管，不得因为「不在本次 diff 范围」就丢弃。**

⚠️ **与下方「跨模块存量问题不要顺手改」不矛盾，两条管的是不同动作：**

| 动作 | 范围内 | 范围外 |
|---|---|---|
| **修** | 应当修（见下方「改动者顺手修掉自己踩到的既有缺陷」） | **不修**（撑大 blast radius、污染 diff、多 agent 并发时冲突） |
| **报** | 报 | 🔴 **必须报** |

即：**范围外的东西「不修但必须报」** —— 沉默才是那条真正的缺陷。

## 关键规则

- 不修改任何文件，仅读取和分析
- 必须读取实际文件内容，不凭文字描述判断
- 🔴 **注释不是实现证据。** 任何「这个能力存在」的结论，引用的 `file:line` 必须落在**可执行语句**上；
  落在注释 / 文档块 / 类型声明上的一律不算。**先数命中、不读原文** 是本仓已实证的误判来源
  （「强制滚到底」4 处命中全是块注释）。
- 🔴 **`grep` 计数不能替代逐条打开。** 报「有 N 处」之前先逐条看它是不是你以为的那类行；
  同族陷阱：字符类漏数字（`[A-Z_]` 不匹配 `E2E_EXIT` 里的 `2`）、BRE/ERE 交替语法差异。
  **「查不到」先怀疑自己的查法**，用一个已知存在的样本做正对照，确认判据真能命中。
- 对每个疑似问题，必须说明为什么认为它是问题（有什么现实路径可以触发？或者为什么不可能触发？）
- 严重度标准：Critical = 错误被吞没可能导致状态不一致 / 数据丢失（如缓存被窗口数据覆盖、消息丢失）；Warning = 代码冗余增加维护负担；Info = 风格建议
- **改动者顺手修掉「自己踩到的既有缺陷」应当认可，不要当越界打回** —— 前提是：
  ① 与本次改动**同一处代码/同一族问题**（不是漫游式重构）；② 在交付里**单独列出并说明**，
  不混进功能改动里蒙混；③ 有对应验证。
  实例（2026-08-10 一批）：改侧滑面板时修掉 `.menu-item` 的 `transition: all` 抢帧违规、
  修掉「隐藏菜单项仍在 Tab 序且 Enter 仍触发」；做搜索时经 `pnpm build` 抓出 `.at(-1)` 超 TS lib target。
  这些都不在原任务书里，但都是改动者在该处必然会碰到的真缺陷 —— **压着不修才是留坑**。
  ⚠️ 反面边界：**跨模块、与本次无关的存量问题不要顺手改**（会撑大 blast radius、污染 diff、
  且在多人/多 agent 并发改同一棵树时极易冲突）。判据是「我不修它，本次改动就带着一个已知缺陷交付吗？」

## 审查范围

## 审查维度（按 test-quality-check skill 的 6 类反模式逐一检查）

针对每个变更的测试文件，按 test-quality-check skill 中定义的 6 类反模式逐一识别：

- **A 假测试 / Tautology** — 测试自己写死字面量
- **B 空壳断言** — `toBeDefined / toBeTruthy / toHaveBeenCalled` 不带参数
- **C 测 mock 不测业务** — mock 掉 SUT 本身
- **D 过度兜底变体** — ≥3 个本质相同 it
- **E 永不失败** — 吞错 / `expect(true).toBe(true)`
- **F 重复覆盖** — 多文件复制粘贴

完整判定标准、反例、正例、反向验证步骤见 [.claude/skills/test-quality-check/SKILL.md]。

### 覆盖缺失（test-quality-check 之外的额外检查）

对照业务代码检查：
- 新增的组件是否有渲染测试 + 交互测试？（CLAUDE.md 最低覆盖要求）
- 核心 Hook / 工具函数 / API 封装是否有对应测试？（至少 1 正常 + 1 异常）
- 错误路径是否被测试覆盖？（请求失败、参数非法、资源不存在、权限不足）
- 边界条件是否被测试？（空列表、超长字符串、并发 / 竞态、undefined props）

### 3.5 动画冲突覆盖（前端 motion 组件专用）

如果本次变更含 `motion.*` 组件（新增 / 修改 variants / 修改对应 CSS transition），必须检查：

- [tests/animation-conflict.test.ts](tests/animation-conflict.test.ts) 的 `MOTION_CONTROLLED_SELECTORS` 注册表是否补了新 selector？
- 该 selector 对应的 CSS 文件路径是否准确？
- `controlledProps` 是否如实列出 framer-motion 控制的属性（transform / opacity / 等）？
- 该测试是否实际跑过？（不只是注册了 selector）

vitest 默认 `MotionGlobalConfig.skipAnimations = true`，渲染测试**测不出** CSS `transition: all` 与 motion variants 抢同一帧的 bug。只有这个静态扫描测试能拦。**漏注册 = 假覆盖**，列为 Major。

判断方法：
1. `git diff --name-only -- tests/animation-conflict.test.ts` 看注册表是否变更
2. 对照本次新增的 `motion.*` 组件 / 改过的 motion variants，逐一核对 selector 在注册表中存在
3. 缺失任一即上报

### 4. 测试隔离问题

- 测试是否依赖其他测试的执行顺序或副作用？（`beforeEach` 是否 reset mock / store）
- mock 是否在 `beforeEach` / `afterEach` 正确清理（`vi.clearAllMocks()` / `mockReset()`），避免跨用例污染？
- 测试是否复用 `tests/setup.ts` 的全局 mock 与 `tests/utils/test-utils.tsx` 的工具，而非各自硬搓？
- 新增组件是否已按 CLAUDE.md「注册新组件必须同时改两处」在 `tests/registry.ts` + `tests/components/registry.test.tsx` 注册？
