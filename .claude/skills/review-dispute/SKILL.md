# 审核争议解决（Agent 对话机制）

当盲审报告中存在不通过项时，**不直接修复**，先通过 Agent 对话判断是误判还是真实问题。

## 第 1 轮：审核 Agent 提出问题

审核 Agent（blind-reviewer）已输出不合格项列表，每项包含：
- 不合格项编号和描述
- 具体原因（代码位置、预期行为 vs 实际行为）
- 严重度（Critical / Warning / Info）

## 第 2 轮：实施 Agent 回应

启动独立 Agent（code-worker 或 architect），针对每个不合格项做出解释：

**Agent prompt 模板**：

```
你是实施方 Agent。盲审报告中以下项被标记为不通过，请逐项回应：

{不合格项列表}

对每一项，做出以下判断之一：
1. **确认问题** — 承认这是真实问题，说明修复方案
2. **解释合理性** — 提供审核 Agent 缺少的上下文，说明当前实现为何是正确的
3. **部分接受** — 接受问题存在但严重度需降级，说明理由

请读取相关代码文件后回应，不要凭记忆。
```

## 第 3 轮：审核 Agent 终审

将实施 Agent 的解释转发给审核 Agent，由其逐项判定：

**Agent prompt 模板**：

```
你是审核方 Agent。以下是实施方对你提出的不合格项的回应，请逐项终审：

{实施方回应}

对每一项，判定：
- **误判** — 实施方解释合理，改为通过
- **真实问题** — 解释不充分，维持不通过并说明理由
- **降级** — 接受严重度降级（如 Critical → Warning）

请读取相关代码文件验证实施方的说法，不要仅凭文字判断。
```

## 对话限制

- 最多进行 **2 轮**对话，避免无限争论
- 2 轮后仍有分歧的，标记为 **待用户裁定**，输出双方观点供用户决定

## 处理结果

- **误判项** — 无需修改，从不合格列表中移除
- **真实问题** — 立即修复，修复后重新提交审核（仅审核修复的部分）
- **待用户裁定** — 列出双方观点，等待用户指示

## 注意事项

- 审核 Agent 和实施 Agent 必须各自**独立读取代码文件**，不可仅依赖对方的文字描述
- 涉及环境变量/配置的争议，必须读取 `.env` 等实际文件确认
- 争议解决后，更新 Plan 的审核报告，记录最终判定结果
