## 第零步：需求对齐（不可跳过）

在进行任何技术分析之前，必须先确认自己完整、准确地理解了用户的原始需求。

### 0.1 收集需求来源

按优先级依次搜索以下位置，找到用户原始需求的完整描述：

1. **用户当前对话** — 用户在本次对话中给出的需求描述、补充说明、纠正
2. **需求文档** — `backend-docs/` 下的功能设计文档、PRD
3. **Issue / PR** — 如果用户提供了 GitHub Issue 或 PR 链接，用 `gh` 命令读取完整内容
4. **历史对话记忆** — 检查 memory 中是否有相关的 project 类型记忆
5. **Git 历史** — `git log --grep` 搜索相关 commit message 中的需求上下文

**如果以上来源都找不到明确的需求描述，必须直接向用户确认需求，不可自行推测。**

### 0.2 需求拆解

将收集到的原始需求逐条拆解为具体的功能点，每个功能点必须包含：

- **功能描述**：用户要什么
- **预期行为**：在什么场景下应该如何工作
- **来源**：这个功能点来自哪里（对话 / 文档 / Issue）

输出格式：

```
### 需求对齐

**需求来源**: [列出找到需求描述的位置]

**功能点拆解**:
| # | 功能点 | 预期行为 | 来源 |
|---|--------|----------|------|
| 1 | ...    | ...      | ...  |
| 2 | ...    | ...      | ...  |
```

### 0.3 用户确认

将拆解结果向用户展示，明确询问：

> 以上是我理解的需求功能点，请确认是否完整、准确。如有遗漏或理解偏差请指出。

**用户确认前不得进入后续步骤。** 如果用户纠正了理解，更新功能点列表后再次确认。

## 反向验证规则（贯穿全流程，不可跳过）

审计中发现的每一个疑似问题，在上报前必须通过反向验证。目的：消除 false positive，只上报经验证的真实缺陷。

### 验证步骤

对每个疑似 finding：

1. **存在性验证** — 涉及字段/函数/变量名的问题，必须 `grep` 确认其存在性。如果不存在，直接丢弃
2. **意图标记检查** — 检查代码中是否有显式意图标记：
   - `_` 前缀变量（刻意未使用）
   - `#[allow(dead_code)]`（刻意保留）
   - 注释中的 TODO/Phase/WIP 说明（分阶段设计）
   - commit message 中的功能定位描述
3. **调用链追踪** — 追踪完整调用链（不止看当前函数），确认：
   - 是否有配套机制在其他地方处理了此问题？
   - 上游/下游是否已经保证了此处无需额外处理？
4. **反面论证** — 主动构造"这不是 bug"的论据。如果能找到合理解释，该 finding 降级或丢弃
5. **对比一致性** — 检查项目中同类操作是否一致。如果只有此处不同，更可能是遗漏；如果全部都不做，更可能是刻意设计

### 上报标准

- 只有反向验证**全部失败**（找不到合理解释）的 finding 才能上报为缺陷
- 反向验证部分成功的 finding，标注为"灰色地带"并附上正反证据
- 反向验证成功的 finding 直接丢弃，不出现在报告中

### 子 Agent prompt 构造规范（启动审计/排查类 Agent 时必须遵守）

当通过 Agent 工具启动子 Agent 执行审计、排查、扫描类任务时，**prompt 中必须嵌入以下内容**，不可只写发现指令而省略验证步骤：

1. **反向验证步骤**（直接复制上面 5 条验证步骤到 Agent prompt 中）
2. **项目已知惯用模式清单**，避免将刻意设计误判为缺陷：
   - **Canary test** — 函数体只有 `check_service()` 守卫，无断言，目的是在测试输出中显示服务状态
   - **Smoke test** — 只验证端点可达和返回类型正确（`is_array()`/`is_number()`），不验证具体值
   - **条件守卫** — `if obs.is_null() { return; }` 模式，用于测试环境中可合法缺失的配置项
   - **预留 API** — `pub fn` 定义了但当前业务代码未调用，为下一阶段功能准备
   - **测试覆盖互补** — 某测试断言较浅，但同一场景在其他测试文件中有更强覆盖
3. **激励校准**：明确告知 Agent「精准度优先于召回率，一个误判比一个漏报代价更高」
4. **风险概率评估**：要求对每个风险评估触发概率（几乎不会/罕见/常见），概率为「几乎不会」的最高标 Low
5. **上下文阅读要求**：判断任何测试/函数前，必须先读文件头注释和函数内注释，不可仅凭名字推断

**反面教训**（2026-04-02）：HG 深度审计中第一轮 Agent 只写了发现指令，未嵌入反向验证，导致 52 个 finding 中 23 个（44%）为误判。t50 文件头第一行就写了 "smoke tests" 但 Agent 没读就判 Critical。

### 第二轮反向排查到具体代码行（强制，每条 finding 不可跳过）

**第一轮 Agent 报告产出后，每条 finding 必须由独立的第二个 Agent（或主对话独立执行）反向排查到具体代码行验证真实性，未通过的 finding 必须丢弃或降级为"灰色地带"。第一轮 Agent 的结论不可直接采信进入修改方案。**

#### 第二轮验证的硬性要求

对第一轮的每条 finding 必须产出以下证据后才允许上报：

1. **精确到行号的存在性证据**：用 `Grep -n` 或 `Read offset/limit` 给出 `文件:行号` 形式的精确位置，不接受"在 xxx.ts 中"这种模糊定位
2. **0 调用方类 finding** — 必须 grep 全 codebase（含 `src/`、`tests/`、`scripts/`、配置文件）输出**完整匹配列表**而非"无匹配"一句话；如有 barrel re-export，必须追溯到终端调用方
3. **超长函数 / 死代码 / 重复块** — 必须 `Read` 文件读出实际行号范围 + 真实内容片段，**不接受**仅凭文件大小或 Agent 印象推断
4. **文档/注释不符** — 必须同时给出"文档原文行号 + 内容"和"实际代码状态"两侧证据
5. **意图标记最终检查** — 在第二轮再次扫描该位置上下 5 行 + 文件头注释，确认无 `_前缀` / `#[allow]` / `TODO` / `Phase` / `预留` / `@deprecated` 等被第一轮 Agent 漏看的标记

#### 反向排查必须使用独立 Agent 或独立工具调用

不可用第一轮 Agent 的 reasoning 复述作为验证。必须重新发起：

- **首选**：启动 `subagent_type=Explore` 的第二个 Agent，prompt 明确"仅做存在性 + 调用方 grep 验证，不做新分析"，给出每条 finding 的具体行号证据
- **次选**：主对话独立用 `Grep` / `Read` 工具调用收集证据，不引用第一轮 Agent 的结论文字

#### 输出格式（第二轮验证后才是最终报告）

```
### 第二轮验证证据（按 finding 编号一一对应）

#### Finding [N]: <一句话症状>
- **第一轮 Agent 主张**: <复述一句>
- **二轮存在性验证**: `Grep -n "<pattern>" <path>` →
  ```
  <实际输出>
  ```
- **二轮调用方验证**: `Grep "<pattern>" src/ tests/ scripts/` →
  ```
  <完整输出 / 0 匹配也要明确写出>
  ```
- **二轮意图标记复查**: <扫描该位置上下 5 行 + 文件头的结果>
- **二轮结论**: 确认 / 降级灰色地带 / 撤销
- **撤销理由**（如撤销）: <具体说明哪个反向验证失败>
```

#### 主对话最终交叉验证（最后一道防线）

第二轮 Agent 报告后，主对话仍必须**自己挑出 30%-50% 的 finding 用 Grep/Read 再次随机抽查**。Agent 报告里写"我已验证"≠ 主对话已验证。这是因为子 Agent 的"已验证"可能仍是 reasoning 复述。

抽查不通过的 finding 全部撤销，并在最终报告中标注"主对话抽查 N 项，N 项通过，M 项撤销"以保持透明。

**反面教训**（2026-05-14）：项目健康检查任务中，第一轮 Agent 把 `getWindowInfo` 标为 0 调用方死代码，主对话 sanity check grep 后发现实际被 `src/main.tsx` 调用。若未做第二轮 grep 直接采纳，会导致误删被调用方依赖的函数。从这次起，"二轮反向排查到具体行号"成为审计流程的硬性步骤，缺一不可。

## 第二步：最佳实践调研（委托 sonnet 执行）

**调研工作委托给 sonnet 模型的 Explore Agent 执行**，降低 WebSearch + 结果处理的 token 成本。opus 仅审阅调研结论并做最终判断。

### 执行方式

启动两个并行 Agent，分别负责外部调研和内部代码搜索：

```
# Agent 1：外部调研（社区方案 + crate 搜索）
Agent(subagent_type="Explore", model="sonnet", prompt="

   - 业界（不限语言）对此类功能的最佳实践和设计模式
   - 已知的坑和注意事项

2. crates.io 可用库
   - 与该需求直接相关的成熟 crate
   - 对每个候选 crate 记录：名称、版本、下载量、最近更新时间、功能说明
   - 评估其成熟度、维护状态

3. 当前项目依赖版本约束（必须兼容）：
   - axum 0.8, tokio 1.x, sqlx 0.8, reqwest 0.12, serde 1.0
```

2. **文件变更清单（含 Agent 分配）** — 逐一列出需要修改/新增/删除的文件，说明每个文件的具体变更内容，**并标注由哪个 Agent 执行**。这是硬性规则，确保 Plan 进入执行阶段时每步的 Agent 委托已确定。

## 第四步：风险评估

对修改方案进行全面风险评估：

1. **破坏性变更** — 是否修改了公共接口、数据结构、数据库 schema？是否影响 API 向后兼容性？
2. **功能影响** — 是否可能导致现有功能回归？列出需要回归测试的功能点
3. **性能影响** — 是否引入新的数据库查询、网络调用、大内存分配？是否影响热路径？
4. **安全风险** — 是否涉及认证/授权逻辑变更？是否有注入/越权风险？
5. **数据库/迁移风险** — 是否需要新的 migration？是否会锁表？是否可回滚？
6. **并发风险** — 是否涉及共享状态修改？是否有竞态条件？
7. **测试兼容性** — 修改是否会导致现有测试失败？特别关注：
   - 新增输入验证规则时，检查测试中使用的边界值是否在验证范围内
   - 修改函数签名/返回值时，检查测试中的断言是否需要同步更新
   - 修改错误类型/错误消息时，检查测试中是否有对错误消息的精确匹配

输出格式：

```
### 风险评估

| 风险类别 | 风险等级 | 说明 | 缓解措施 |
|----------|----------|------|----------|
| 破坏性变更 | 高/中/低/无 | ... | ... |
| 功能影响   | 高/中/低/无 | ... | ... |
| 性能影响   | 高/中/低/无 | ... | ... |
| 安全风险   | 高/中/低/无 | ... | ... |
| 数据库风险 | 高/中/低/无 | ... | ... |
| 并发风险   | 高/中/低/无 | ... | ... |
| 测试兼容性 | 高/中/低/无 | ... | ... |

**综合风险等级**: [高/中/低]
```
