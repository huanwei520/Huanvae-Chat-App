# 下载器换方案调研 —— 结论收口（一页）

> **一句话回答**（huanwei 反复问的就是这个）：
> **不换库。** 慢的根因不是 reqwest 不行，是 **HTTP/2 流控窗口没设**（落在协议默认 64 KiB），
> 加两行把窗口调大即可 —— 单流实测 **6.31 → 10.95 MB/s（1.73x）**，已追平乃至略超 Chromium。
> **换成熟方案（aria2 / curl / 换 HTTP 库）解决不了这个问题，因为问题不在库。**

- **决策日期**：2026-08-11 ｜ **状态**：已落地（v1.1.29 起生效）｜ **决策人**：huanwei 线
- **代码**：`src-tauri/src/updater_download.rs`（桌面）· `src-tauri/src/android_update.rs`（安卓）
- **完整推理与实测原始表**：就在上述两个文件的 `build_client` 上方注释里（不另存一份，避免两处漂移）

---

## 1. 根因（为什么"慢"不是库的锅）

reqwest 的三个 h2 窗口旋钮**默认全关**，不发 SETTINGS 覆盖 ⇒ 落到协议默认
**65535 字节**（`h2` crate 的 `DEFAULT_INITIAL_WINDOW_SIZE`）。

**单条 h2 流的吞吐上界 ≈ 窗口 ÷ RTT**，与链路带宽无关 —— 64 KiB 窗口在 30ms RTT 上就是 ~2 MB/s。

⇒ 关键认识：**此前"必须开 8 分片才追得上浏览器"，是拿并发在替窗口还债** ——
8 条 TCP 各拿一份 64 KiB 窗口，聚合起来才把速度堆上去。窗口一放大，单流自己就够快了。

## 2. 改法（两行，已落地）

```rust
.http2_initial_stream_window_size(4 * 1024 * 1024)
.http2_initial_connection_window_size(8 * 1024 * 1024)
```

## 3. 实测（同机 / 同 URL / 交错 A-B 取中位数）

| 变体 | 单流 | 8 分片 |
|---|---|---|
| 改前（reqwest 默认 = 64 KiB 窗口） | 6.31 MB/s | 12.54 MB/s |
| **改后（本决策的两行）** | **10.95 MB/s** | **17.46 MB/s** |
| 对照：Chromium（单连接） | 10.50 MB/s | — |

单流 **1.73x**、分片路径 1.39x。**改后单流已追平/略超浏览器。**

**独立复现**（2026-08-11 另一 worker、另一套 harness、拉丁方轮换消位次偏差、12 轮）：
单流 tuned/default **1.62x**、同轮配对更快 8/10 —— 与上表 1.73x 同量级，**结论可复现**。

## 4. 🔴 不要开 `http2_adaptive_window(true)`（两条独立理由，都实测过）

1. **实测更差**：自适应单流仅 **4.07 MB/s**，不但低于改后的 10.95，**连改前的 6.31 都不如**
   （同轮配对仅 3/14 轮更快，中位比值 0.63x；独立复现得 0.61x）。
   成因：它的窗口探测爬升期，反而拖垮"几秒就结束"的短下载。
2. **它会覆盖上面那两行**（reqwest 官方文档原话：Enabling this will override the limits set in
   `http2_initial_stream_window_size` and `http2_initial_connection_window_size`）
   ⇒ 打开它等于把本决策**静默作废**。

## 5. 为什么不换库（逐个否掉）

| 候选 | 否掉理由 |
|---|---|
| 换 HTTP 库（ureq / hyper 裸用 / isahc…） | 根因是**流控参数没设**，不是库能力缺失。换库要重写 TLS 钉扎、进度上报、分片续传、Range 回退，**换来的仍是同一个默认窗口** |
| 外挂 aria2 / curl 二进制 | 多一个**发货二进制**要签名/公证/脱敏/随版本维护 —— 本仓已因"发货二进制来源不明"吃过两起生产故障；为一个两行能解的问题引入它，代价不对等 |
| 只靠加大分片数 | 那正是**在替窗口还债**；且分片数越多越吃连接数与服务端限流，治标 |

## 6. 边界（如实标注，别当成全平台结论）

- 实测在**桌面 macOS + 特定出口**上做的；安卓侧那两行**未单独测速**，
  沿用"窗口是协议级上界、与平台无关"的推断。
- 复现环境出口存在透明代理（fake-IP 段），**绝对值只对该路径成立**；
  有意义的是**比值**，而比值经两套独立 harness 复现一致。
- 若将来对端降级到 HTTP/1.1，这两行不生效（h2 专属）—— 那种情况下慢的原因另属别处，别拿本页当结论。

## 7. 统一下载器已落地（2026-08-27，线C' 四环 PASS 沉淀）

> 来源：run-1787814943 四份 PASS 交付（单A de701c1e / reviewA 11580a72 / 单B af131586 / reviewB 083a2b85）。本节为 EOF 追加，不改上文任何一行。

`src-tauri/src/unified_download.rs`（新建，1364 行——取数时刻 2026-08-27，现查命令 `wc -l src-tauri/src/unified_download.rs`，行号引用前请先现查）是聊天文件与头像的统一下载引擎：

- **Range 分片**：≥4MiB 走 8 片并发，小于则单片；每片请求挂条件头（validator，见下条）；响应必须是 206 否则报错。
- **断点续传**：复用 `resume_meta.rs` sidecar（零改动）；续传键 = identity（消息面 file_uuid / 个人文件面 file_hash / 头像文件名）+ ETag，**不按 URL 相等判** —— 预签名 URL 3 小时轮换不影响续传；URL 过期（403）时 sidecar 保留，重取新 URL 后从断点继续。
- **重试**：每片最多 3 次、300ms×attempt 退避；URL 过期与远端变更两类错误不重试、直接上浮。
- **校验**：收口尺寸断言 → content_hash 采样 SHA-256 自算 → 有期望值则对账，不一致丢 part+sidecar 报 HV_HASH_MISMATCH。
- **降级**：探测回 200（源不支持 Range）⇒ 单流整拉 + 读 idle 超时 + 整体重试 3 次 + 不写 sidecar（不支持 Range 就没有可信偏移，每次重试 truncate 从头）。
- **超时**：connect 15s + 读 idle 60s，**无含 body 读完的总时长**（GB 视频下任何总时限都是错误的门）；client 显式 `.no_proxy()`（理由见 [rust-dev.md](rust-dev.md) 末节——默认 builder 的系统代理检测在本工作区分钟级卡顿）。
- **接入**：`download_and_save_file`（download.rs）签名一字未动、内部改走引擎，进度事件语义不变；头像 `download_avatar`（storage.rs）同走引擎（part 落 avatars_dir，成功后先删再 rename——Windows rename 不能覆盖）；前端 0 改动。

### MinIO 实测结论：续传 validator 用 If-Match，不能用 If-Range

生产探针（真实预签名 URL、只读 GET，run-1787814943 单B 证据 02）：MinIO **忽略 If-Range**（伪造 ETag 也回 206，等于不校验）、**遵守 If-Match**（伪造 ETag 回 412）。⇒ 分片续传请求挂 `If-Match: <ETag>`；412 语义 = 远端已变 ⇒ 丢 part+sidecar 整份重下。仅有 Last-Modified 无 ETag 时退 `If-Unmodified-Since`。

### Range 支持探测不能用 HEAD（403 陷阱）

HEAD 在按方法签名的网关（SigV4）下回 403 ⇒ **探测 Range 支持用 `Range: bytes=0-0` 的 GET**，看回 206（支持）还是 200（不支持 ⇒ 走降级单流）。

### 登记待办（单B 残留，reviewB R1~R3，三条的失败方向均安全、不阻塞）

1. **降级路径无「已降级」日志**——降级分支函数体内零上报语句（正对照：分片主路径有 2 条）。主路径今天有实测证据，非现存缺陷；建议后续卡在降级入口加一行日志，别让兜底路径静默。
2. **sidecar 落盘非原子**（std::fs::write 直写目标路径），与周期落盘有极小并发窗口——失败方向安全：清单损坏一律按无断点重下，can_resume 与哈希双闸保证拼不出坏文件。建议改 temp+rename。
3. **part 写入无 fsync**，机器级断电可让 sidecar 的 done 计数超过盘上真实字节——旧单流实现同级、非回归；消息面（无服务端期望值）对账兜不住这一态，记录备查。

### 8.2 中断/续传：`kill -9` 于 1.5GB，读数与方向

中断方式是**独立进程 + SIGKILL**（`rc=137 = 128+9`），理由是 SIGKILL **不可捕获不可屏蔽** ⇒ 引擎零善后机会；
Ctrl-C / SIGTERM / 代码内 return 都会留一条「临终落盘」的路，那测的是**优雅退出**、不是**断点耐久性**。

| 量 | 值 |
|---|---|
| 中断时在途进度 | 1,528,571,656 |
| sidecar 记的 `sum(done)` | **1,520,729,288** |
| 差 | 7,842,368 B（1s 节流的持久化滞后，11–12 MB/s × ~0.7 s，量级吻合） |

🔴 **方向是保守的，这才是承重的那句**：清单 **≤** 盘上真实字节 ⇒ 续传时那 7.8MB 被**再下一遍**（多下），**不会被跳过**（漏字节）；
**反方向（清单 > 真实）才会拼出坏文件**，本次未出现。终值全量 SHA-256 相等 ⇒ 那 7.8MB 确实没被漏掉。

sidecar 8 片闭区间首尾相接、每片 558,275,408、合计恰好铺满 `[0, 4466203264)`、`last_end = total−1`（单2 用 python 独立重算）。
⚠️ 续传键是 **identity + ETag 不是 URL**（`src-tauri/src/resume_meta.rs:94` 的 `can_resume`），
但 sidecar 里那个 JSON 字段名却叫 `"url"`（历史遗留命名）⇒ **排障时极易误判成「按 URL 判续传」**。建议下次动这块时顺手改名。

### 8.3 🔴 「只补缺失字节」的取证法（可照抄）

**做法**：`netstat -ib` 在续传 run 前后各取一次，取 `en0` 的 `Ibytes` 差。

| 量 | 值 |
|---|---|
| 总量 / 断点 / **缺失量** | 4,466,203,264 / 1,520,729,288 / **2,945,473,976** |
| 续传 run 网卡实收 | **3,131,746,796** |
| / 总量 | 0.7012 |
| / 缺失量 | **1.0632** |

**为什么它有判别力（这一段是方法，不是数字）**：要否证的命题是「**它其实重下了全量**」。
`netstat` 给的是**整机**计数（≥ 本进程），是被测量的**上界**；若真是从头重下，实收必须 **≥ 4,466,203,264**。
**上界（3.13 GB）没够到下界（4.47 GB）⇒ 结构性否掉**，不是「接近」是「不可能」。
⇒ 🔴 **跨进程这一维的混淆让结论【变强】，所以它反而是这条证据的优点。**

🔴 **但【跨接口】那一维会让它变弱，必须另外排除** —— 只取 `en0`，若流量走了别的接口 `en0` 就会**少计**，
那才会把「3.13 < 4.47」变成假象。两条判据排除它：
① **开销系数 > 1**：前一个 run 的 `en0 收 1,628,088,528 / 在途落盘 1,528,571,656 = 1.0651`（TLS record + TCP/IP 头）——
有流量漏到别的接口时这个比值会掉到 1 以下；
② 同批 `netstat` 里 `utun0 / lo0 / en1` 的增量分别是 2.3MB / 0 / 0 量级 ⇒ **没有第二条承载接口**。

**反推**：3,131,746,796 ÷ 1.0651 = **2,940,331,232**，缺失量 2,945,473,976 ⇒ **相差 −0.17%**
⇒ 不只是「没有整整多下一遍」，而是**连一次可观的重复下载都没有**。
另量了背景噪声：两个 run 之间 29 秒空窗的 `en0` 增量 778,790 B ⇒ 26.9 KB/s ⇒ 推到 239 秒窗约 6.4 MB，占 0.2% ——
**整机与进程之差在本次实测里就是这个量级**。

⚠️ **这条证据能证什么、不能证什么（写死，别外推）**：它只证「续传搬的**体积** ≈ 缺失量」，
**不证「搬的是正确的那些偏移」**。后者由**全量 SHA-256**（把源站对象整个再流一遍边算边比，覆盖 100% 字节，
`local == remote`，负对照「本地少 1 字节」⇒ false ⇒ 比对会响）承担。**两条合起来才是完整论证，缺一条都不完整。**

补充的第二条独立锚：耗时与**缺失量**成比例而非与总量 —— 两 run 速率 12.32 / 12.34 MB/s（比 1.0014），
反事实「从头重下需 362.5 s」vs 实测 238.77 s = **65.9%**，而 缺失/总量 = **66.0%**，对到小数点后一位。
⚠️ 但它依赖「两次链路吞吐相同」这个假设（本次成立，换个网络波动时段就未必）⇒ **它是旁证，`netstat` 那条才是结构性的**。

### 8.4 内存口径订正（别照抄错的那句）

🔴 macOS `/usr/bin/time -l` 的 `maximum resident set size` 取自 **`RUSAGE_CHILDREN`** ⇒ 它是
**「本进程与其子进程中的最大值」= 一个上界**，**不是**「只有本进程」。
本次因 harness 未 fork 任何子进程（8 个分片是同进程内的 tokio task）才等于本进程峰值。
⇒ **写成「不含子进程」是把上界说成了等值**；方向仍安全（上界只高估不低估），但措辞不准。
交叉印证：另一口径（每秒 `ps -o rss=`，107 个样本）得 16,924,672 B，两者差 2.4%。
⚠️ 每秒采样的峰值可能被采样间隔漏掉 ⇒ 16.5MB 是**下界**；而要的结论是「不随下载量增长」，方向同样安全。

### 8.7 消息面**不做**哈希对账 —— 本次终值正确性不压在引擎自算的哈希上

消息面 `cache_key` 是 `file_uuid`，不满足 `src-tauri/src/download.rs:192` 那一行的判据（64 位十六进制）
⇒ `expected_sampled_hash` 未被填 ⇒ **`HV_HASH_MISMATCH` 这条路整个没被触发**，引擎只是自算了一个哈希作身份/去重。
且采样哈希对 >30 MiB 的文件只喂「size 前缀 + 头/中/尾各 10 MiB」⇒ **对这个 4.16 GiB 文件只覆盖 0.7%**。
⇒ **「终值正确」这个结论压在全量 SHA-256 上，不压在它身上。**

一条**未被机制证实**的强巧合（当线索用，别当证据）：服务端对象 key 里那 8 位十六进制段与引擎下载后自算的 sampled_hash 前 8 位**逐字相同**（`0ef17d96`），
且 App 的 TS 上传侧按同一套采样规则算内容哈希（`src/hooks/useFileUpload.ts` 里 SAMPLE_SIZE 与阈值与 Rust 侧同值）。
⚠️ 但「服务端用客户端哈希给对象命名」这条规则的**真值源在后端仓，本仓查不到** ⇒ 它是「数值巧合极强」，**不是「机制已证」**。

### 9.2 🔴 三个界面事实 + 一条未归因观察 —— 断网后 UI 先假装、再把这件事抹掉（本节最重要的产出）

   ⇒ **用户能察觉的唯一信号是「我点过的那个下载不见了」** —— 这比「假装还在下」更难排查。
